# Nib — AI 时代跨平台桌面框架 · 设计文档 v0.1（草案）

> 状态：草案，供讨论
> 日期：2026-09-21
> 命名状态：候选名「Nib」，待最终确认（见附录 A）

---

## 1. 背景

### 1.1 问题：Electron 为什么大

Electron 应用必须完整打包一份 **Chromium（约 70–150MB）+ Node.js 运行时（约 40–60MB）**。
即使是最简单的应用，安装包也在 100MB 以上，内存占用 200–500MB，冷启动 2–5 秒。
优化手段（tree shaking、asar、删语言包、二次压缩）一般只能压到 30–60MB，
无法突破 Chromium 本身的体积下限。

### 1.2 现有替代路线的验证与局限

**Tauri（Rust + 系统 WebView）**——验证了"借系统 WebView"路线可行，但：

- Rust 学习曲线劝退了核心用户群（前端/应用开发者）
- 依赖系统 WebView 导致碎片化测试成本高（WebView2 / WKWebView / WebKitGTK 行为不一）
- 生态时间差：比 Electron 晚 7 年，插件、案例、踩坑资料都少
- 存量锁定：大量 Electron 应用没有迁移动力

**Wails（Go + 系统 WebView）**——验证了"低门槛后端语言"路线可行，但存在明确痛点：

| # | Wails 痛点 | 本框架的应对 |
|---|-----------|-------------|
| 1 | 单进程架构，后端 panic 或 WebView 崩溃 = 整个应用退出 | 主进程/渲染进程隔离，崩溃恢复对用户透明（支柱一底座） |
| 2 | 无任何权限模型，绑定方法对前端全开放 | 声明式权限注解，默认拒绝（支柱三） |
| 3 | 深度系统 API（macOS 截屏、托盘等）要自己写 CGO/ObjC 并长期维护 | 官方系统能力包，把社区重复造的轮子官方化（M4） |
| 4 | 没有官方自动更新 | 增量更新内置为一等公民（支柱四） |
| 5 | IPC 只有请求-响应，流式场景（进度、日志、大文件）凑合 | call / stream / event 三类绑定一等公民（支柱一） |
| 6 | 错误跨边界传递是黑洞（error 变成字符串） | 跨边界错误信封，因果链缝合（支柱一） |
| 7 | 首次/增量构建编译 Rust 极慢（首构 ~340s） | Go 后端，增量编译 <1.5s 作为硬指标（北极星） |
| 8 | 运行时不可观测，AI 拿不到结构化信息 | 事件流 + 无头驱动 + 错误信封（支柱一/二） |

**市场空档 = Wails 的开发体验 + Tauri 的安全模型 + 两者都没有的"机器可操作性"**

### 1.3 结构性变化：框架的用户一半是 AI

AI 时代，框架用户的构成变了：代码由 AI 写、调试由 AI 做、验证由 AI 执行。
由此推出两个设计基设：

1. **迭代回路速度取代功能数量，成为框架的核心指标**（详见第 3 节）
2. **框架的工具链必须假设操作者是 AI agent**（CLI 输出结构化、运行时无头可驱动）

### 1.4 明确不做的事（非目标）

- ❌ **AI 运行时**（llm 抽象、模型管理、embedding、function calling 打通）——这层变化太快、
  不是框架的职责、做不过专门厂商。框架只保证"接 AI 能力的通道好用"（流式 IPC、绑定生成）。
- ❌ 裁剪 / 魔改 Chromium——历史上无数项目证明此路不通，且违背"借系统 WebView"的前提。
- ❌ 第一阶段不做移动端——先把桌面做穿，移动端作为远期方向保留架构余地。

## 2. 定位

> **一个"系统 WebView 壳 + Go 核心"的轻量跨平台桌面框架：
> API 面为 LLM 优化，工具链为 AI agent 设计，发行形态面向高频迭代。**

体积目标：Hello World 安装包 **<10MB**；内存占用 **<50MB**；冷启动 **<1s**。

预期指标对比（基于公开基准测试数据）：

| 指标 | Electron | Tauri | Wails | **Nib（目标）** |
|------|---------|-------|-------|----------------|
| 安装包 | 100–300MB | 3–12MB | 8–15MB | **<10MB** |
| 空闲内存 | 200–500MB | 40–80MB | 50–90MB | **<50MB** |
| 冷启动 | 2–5s | 0.3–1s | 0.5–1.5s | **<1s** |
| 增量编译 | 快 | 慢（首构 ~340s） | ~12s | **<1.5s** |

---

## 3. 北极星指标：AI 单次迭代时间 T_iter

AI 开发桌面应用的真实循环：

```
生成代码 → 编译 → 启动应用 → 观察结果 → 带上下文修复 → 再生成
   ↑___________________________________________________|
```

**T_iter = t_compile + t_launch + t_observe + t_context**

| 变量 | 含义 | 目标 | 手段 |
|------|------|------|------|
| t_compile | 增量编译时间 | <1.5s | Go 后端；依赖膨胀管控（构建时报告编译时间退化，超阈值告警）；绑定生成器增量 |
| t_launch | 应用启动时间 | dev 下 ≈0 | 常驻开发外壳：窗口/WebView 永不死，只热替换后端业务层（见 5.3） |
| t_observe | 观察结果耗时 | <1s | 事件流 + 一键截图 / DOM 快照导出 + 无头驱动（见 5.5、支柱二） |
| t_context | 收集错误上下文 | 一次到位 | 跨边界错误信封：JS 栈 → IPC 记录 → Go 栈缝合成单一因果链（见 5.4） |

**端到端目标：T_iter < 5 秒**（对照：Wails 约 10–20s，Tauri 分钟级）。

## 5. 底座：核心运行时

### 5.1 技术选型

- **后端语言：Go**——编译快、标准库强、静态链接单二进制、开发者池大
- **渲染：系统 WebView**——Windows 用 WebView2，macOS 用 WKWebView，Linux 用 WebKitGTK
- **WebView 绑定：CGO 薄封装**——三个平台各约 1000–1500 行平台相关代码，是整个框架
  唯一绕不开的平台相关层；可参照 zserge/webview 的实现思路
- **前端技术栈不限**：React / Vue / Svelte / 原生 HTML 皆可，框架只约定 IPC 协议

### 5.2 绑定生成器（核心引擎之一）

用户在 Go 中定义服务，框架生成类型安全的 TS 客户端。**三类一等公民**：

```go
// call：请求-响应
type GreetService struct{}

func (g *GreetService) Greet(name string) (string, error) {
    return fmt.Sprintf("Hello %s!", name), nil
}

// stream：双向流（进度推送、日志、大文件分片），自动生成 AsyncGenerator + 背压 + 取消
// @binding stream
func (t *TaskService) RunPipeline(input string) (<-chan Progress, error) { ... }

// event：广播
// @binding event
func (b *BusService) FileChanged() <-chan FileEvent { ... }
```

```typescript
// 自动生成的 TS 绑定——类型完整，前后端编译期同步
import { GreetService } from '../bindings/main';
const result: string = await GreetService.Greet("World");
```

- 实现：Go AST 解析（go/ast + go/types）→ 提取签名 → 生成 TS 接口 + IPC 存根
- 增量：改一个方法签名只重新生成受影响的部分
- 这是 Wails 最优雅的设计，直接继承并扩展（Wails 只有 call 一类）

### 5.3 Dev Harness：常驻开发外壳

现状（Wails 亦如此）：改 Go 代码 → 杀掉应用 → 重建窗口和 WebView（300–500ms）→ 丢状态。
对 AI 迭代是固定税。

```
[常驻层] 窗口 + WebView + 前端 HMR        ← 永远不死
   ↕ IPC（本地 socket）
[可替换层] 用户的 Go 业务代码               ← 改动后 <1s 热替换，状态可选保留
```

- 业务层以接口边界隔离，热替换 = 重启业务层 goroutine 组，而非整个进程
- 前端 HMR 走 WebView 的 dev server 注入
- 验收标准：改一行业务逻辑 → 界面更新，**窗口无闪烁、总耗时 <2s**

### 5.4 跨边界错误信封

问题：JS 调 Go 出错时只能拿到字符串，AI 不知道错在哪一层。设计成单一错误格式贯穿两边：

```json
{
  "error": {
    "code": "fs.read/permission_denied",
    "message": "read /etc/passwd: operation not permitted",
    "chain": [
      {"layer": "js",  "frame": "App.tsx:42 handleClick"},
      {"layer": "ipc", "call": "fs.read", "args_digest": "path=<redacted>"},
      {"layer": "go",  "frame": "fs_service.go:88 os.Open"}
    ],
    "retryable": false,
    "doc": "https://nib.dev/errors#fs-permission"
  }
}
```

要点不在格式本身，而在**因果链**：JS 调用栈、IPC 记录、Go 栈帧缝合成一条。
附带的纪律：Go 端 panic 一律转为结构化错误返回，不穿透到前端。

### 5.5 运行时事件流（可观测性底座）

运行时把每个窗口事件、每次 IPC 调用、每个文件操作、每次 panic 都发为结构化事件：

- 开发时进入一个内置 inspection 页面（给人看）
- CLI 可 `--json` 流式导出（给 AI 看）
- 安全层（支柱三）复用同一份数据出系统调用报告——**安全是观测数据的第二个视图，不是另起炉灶**

## 6. 支柱一：LLM 友好的 API 面

目标：AI 写本框架代码时**幻觉率低、猜得准、编译快**。

- **单一语言全栈**：Go 后端 + 生成 TS，AI 只维护一个语言上下文
- **极小且规律的 API 表面积**：严格命名规范（`fs.read` / `win.create` / `dialog.pick`），
  能推断的不允许配置，约定优于配置
- **机器可读文档**：构建时自动生成 `llms.txt` + API manifest（全部绑定方法的 JSON Schema），
  AI 直接消费
- **编译速度硬约束**：增量编译 <1.5s 写入验收标准；CLI 报告编译时间退化
- **错误信封**（见 5.4）：AI 一次拿到完整因果链，修复成功率与孤立字符串完全不同

## 7. 支柱二：机器可操作的工具链

目标：框架的一半用户是 AI agent，工具链按此前提设计。

- **CLI 全命令 `--json` 结构化输出**，错误 = 错误码 + 修复建议 + 文档链接，AI 读完能自己修
- **无头驱动模式**：`app --headless --driver-port 9400`，暴露简化版 CDP 协议——
  模拟点击、填表、调用绑定方法、读事件流、截图、导出 DOM 快照 / accessibility tree。
  **AI 写完代码可自跑 E2E 验证，不需要人看 GUI**
- **MCP server 内置**：框架运行时挂 MCP，AI 助手可操作应用做调试与验证
- **app.spec 驱动脚手架**：spec 描述页面、数据模型、能力清单——
  **人机协作界面上移到 spec，人改 spec 而不改代码**
- **`nib doctor` 环境自检**：AI 配环境最易默默失败，doctor 把工具链问题变成结构化报告

CLI 命令设计：`nib new` / `nib dev` / `nib build` / `nib doctor` / `nib ship` / `nib audit`

## 8. 支柱三：面向不可信代码的安全模型

目标：AI 生成的代码审不过来，让框架把**审计面收敛到一份 manifest**。

- **声明式权限注解**：绑定方法显式声明所需权限，**默认拒绝**——未声明的方法前端不可见；
  在绑定生成时做编译期检查（借鉴 Tauri capability，但前置到生成阶段）
- **构建时依赖审计**：扫描依赖树并对接漏洞库；AI 爱乱引依赖的问题在构建期暴露
- **`nib dev --sandbox`**：网络/文件访问全部记录成结构化报告，人审报告而不是审代码
- 设计顺序：先做支柱二的事件流（系统调用本就被记录），安全层**长在观测数据上**

## 9. 支柱四：高频迭代的发行形态

目标：AI 时代发布节奏是**一天多版**，把"快"当默认场景。

- **增量更新内置**：差分包 + 签名校验 + 原子替换 + 失败回滚（Wails 没有、Tauri 才有的事，做成标配）
- **UI 声明式动态下发**：UI 层 DSL 可从服务端拉取，改界面不发版——
  AI 生成 UI → 审核 → 热更新，快速实验成本趋近于零
- **功能模块按需加载**：应用骨架 + 按需求载的能力包，安装包保持极小

## 10. 里程碑

| 里程碑 | 内容 | 验收标准 | 依赖 |
|--------|------|---------|------|
| **M1：能跑** | Go + WebView 最小运行时、绑定生成器（call 类）、常驻外壳热替换 | Hello World 三平台可运行；改业务代码 → 界面更新 <2s | — |
| **M2：能诊** | 错误信封、事件流、CLI `--json`、无头驱动 + 截图/DOM 导出 | AI 拿到错误能定位因果链；无头模式可脚本化驱动应用 | M1 |
| **M3：能信** | 权限注解（默认拒绝）、依赖审计、沙箱报告 | 未声明权限的方法前端不可见；`--sandbox` 产出系统调用报告 | M2（事件流是地基） |
| **M4：能发** | 增量更新 + 回滚、stream/event 绑定、UI 动态下发、官方系统能力包 | 差分更新可用；改 UI 不发版 | M2 |

M3/M4 可并行；M1 是一切的前提。

## 11. 杀手级 Demo 愿景

> **"一句话，3 分钟，生成一个可用的桌面应用"**

```
输入需求
 → AI 生成 app.spec
 → 框架生成代码（API 面小 → 生成质量高）
 → 编译（<2s）
 → 权限声明自动生成待审（M3）
 → 无头自测 + 截图验证（M2）
 → 增量发布（M4）
```

每一环都有明确的框架能力兜底，没有一环是口号。

## 12. 竞品教训速查

- **Electron**：体积是结构性的（自带 Chromium + Node），优化有下限；护城河是生态与存量，不是技术。
- **Tauri**：架构正确，败在 Rust 门槛吓跑核心用户群 + WebView 碎片化测试成本；优势是安全模型与移动端，值得借鉴前者。
- **Wails**：证明了"Go + 系统 WebView + 自动绑定"可行，开发体验是它的王牌；
  但单进程、无权限模型、无自动更新、运行时不可观测，给后来者留了明确空档。
- **Compose Multiplatform**：另一条路（自带 Skia 渲染），JRE 决定体积下限 40MB+，不是本框架的竞争维度。

| 候选 | 含义 / 故事 | nib.dev 同级 .dev 域名 | npm | 结论 |

| Tern | 燕鸥：小而快的候鸟 | ❌ 已注册 | ⚠️ 被占 | 放弃 |
| Recur | 迭代/递归：直指北极星指标 | ❌ 已注册 | ⚠️ 被占 | 放弃 |
| Petrel / Cowrie / Takt / Plover / Gosling | 海燕 / 货贝 / 节拍 / 鸻 / 雏鹅 | ❌ 均已注册 | 部分被占 | 放弃 |

**推荐：Nib**

- 故事贴合定位："AI 时代，代码由笔（AI）写成，框架是笔尖"——小、准、快正是框架的特质
- CLI 体验极佳：`nib new` / `nib dev` / `nib doctor` / `nib ship`
- 包管理策略：npm 用 `@nibjs/*` scope，Go module 用 `nib.dev/*`（注册 nib.dev 后生效）
- 风险：英文 nib 另有"咖啡烘烤程度"之意，无伤大雅

若对 Nib 不满意，备选顺序：Inklet > Whelk。
